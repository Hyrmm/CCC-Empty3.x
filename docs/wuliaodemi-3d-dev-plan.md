## 3. 需求理解与版本范围

### 3.1 PDF 中的核心玩法

玩家目标：

1. 在一个碗中逐颗点击并捡出米粒与目标豆子。
2. 本关要求玩家把全部目标绿豆捡出来。
3. 玩家在捡完之后输入本关绿豆数量。
4. 输入正确则过关，解锁下一关。

核心表现要求：

- 米和绿豆不是平铺，而是堆成一个小山状。
- 上层颗粒被取走后，下层颗粒逐渐露出。
- 绿豆展示区在下方分区显示。
- 错误输入、时间不足、展示区解锁都可通过广告获得辅助。

### 3.2 首个正式版本建议范围

建议将首发版本控制为 **MVP + 可上线版本**，避免第一版范围过大。

#### V1 必做

- 新手引导关
- 关卡模式
- 3D 碗内米粒/绿豆堆叠与点击拾取
- 关卡计时
- 数量输入与判定
- 绿豆展示区与广告解锁
- 输入错误后的广告提示
- 超时后的广告加时
- 本地存档
- 成就统计
- 地域排行
- 基础分享能力
- 音效、震动、基础特效

#### V1.1 可补充

- 关卡难度曲线优化
- 每日任务
- 主题皮肤
- 更多豆子美术变体
- 数据埋点后台
- 远程配置

#### 暂不做

- 自定义模式
- 复杂物理模拟
- 多人实时玩法
- 大地图或开放场景

## 4. 核心设计决策

### 4.1 采用“3D 场景 + 2D UI”混合方案

建议使用：

- 3D：碗、桌面、米粒、绿豆、摄像机、光照、拾取动画
- 2D UI：倒计时、关卡信息、输入面板、豆子展示区、广告按钮、结算弹窗

原因：

- Cocos Creator 3.x 的 3D 能力足够支撑轻量拟真视觉
- 2D UI 继续复用当前 `UIMgr` 更高效
- 纯 3D UI 开发成本高，不利于首版快速落地

### 4.2 不使用真实物理堆叠，改用“伪物理 + 逻辑层级”

不要让数百上千颗米粒全部挂 `RigidBody` 和 `Collider` 做实时物理。

建议方案：

- 用算法生成一堆“逻辑颗粒”
- 每个颗粒有自己的三维坐标、遮挡关系、是否可点击状态
- 仅渲染当前可见和临近可见的颗粒
- 点击后更新遮挡关系，再刷新露出层

原因：

- 手机端真实物理成本过高
- 点击玩法不需要真实碰撞反馈
- 逻辑堆叠更容易控难度、控性能、控视觉一致性

### 4.3 首版只做“关卡模式”

PDF 中自定义模式已标注“先不做”，建议完全从代码结构上预留，但不进入首轮排期。

## 5. 玩法循环设计

单局完整流程如下：

1. 进入关卡。
2. 根据关卡配置生成米粒总数、绿豆总数、展示区分区数、倒计时。
3. 初始化碗内颗粒堆。
4. 玩家点击可见颗粒。
5. 若点到米粒，则米粒飞出并计入统计。
6. 若点到绿豆，则飞入下方绿豆展示区，并计入统计。
7. 被遮挡的下层颗粒逐步露出。
8. 玩家在全部绿豆被捡出后，输入绿豆数量。
9. 输入正确则通关，否则触发错误反馈。
10. 如果倒计时结束但未完成，可观看广告获得加时。
11. 如果输入错误，可观看广告获得范围提示。
12. 结算并写入本地存档与排行增量数据。

## 6. 3D 核心实现方案

### 6.1 3D 场景结构

建议主场景节点结构：

```text
MainScene
|- WorldRoot
|  |- CameraRoot
|  |  |- MainCamera
|  |- LightRoot
|  |  |- DirectionalLight
|  |  |- FillLight
|  |- StageRoot
|  |  |- Table
|  |  |- Bowl
|  |  |- GrainRoot
|  |  |- EffectRoot
|  |- DebugRoot
|- Canvas
|  |- UIRoot
```

说明：

- `GrainRoot`：米粒与绿豆实例节点池
- `EffectRoot`：拾取动效、闪光、粒子
- `Canvas/UIRoot`：继续复用现有 UI 管理框架

### 6.2 摄像机方案

建议固定镜头，不做自由旋转。

推荐参数：

- 俯视角：35° 到 50°
- 轻微透视
- 镜头固定在碗正前上方
- 关卡中不允许拖拽旋转镜头

原因：

- 保证触点映射稳定
- 便于设计“上层被拿走，下层露出”的视觉阅读
- 减少玩家误触

### 6.3 颗粒对象设计

建议定义统一颗粒结构：

```ts
export enum GrainType {
  Rice = 1,
  Bean = 2,
}

export interface GrainData {
  id: number;
  type: GrainType;
  layer: number;
  localPos: Vec3;
  rotation: Vec3;
  scale: number;
  exposed: boolean;
  collected: boolean;
  blockersAbove: number[];
  supportsBelow: number[];
}
```

说明：

- `layer` 表示所处逻辑层
- `blockersAbove` 表示上方遮挡自己的颗粒
- `supportsBelow` 用于做露出刷新
- `exposed = true` 的颗粒才允许点击

### 6.4 碗内堆叠生成算法

建议采用“圆碗区域 + 分层采样 + 上层收缩”的方式生成堆。

#### 生成思路

1. 根据关卡配置决定总颗粒数与绿豆数。
2. 先生成逻辑层数，例如 `6 ~ 14` 层。
3. 每层在碗口有效半径内随机采样若干点。
4. 越高层半径越小，形成小山效果。
5. 将绿豆随机插入各层，但要控制上层至少有少量绿豆可见。
6. 依据平面距离和层级关系，建立遮挡引用。

#### 关键约束

- 任意时刻可点击颗粒不能过少，否则手感差。
- 绿豆不能全部埋在底层，否则玩家前期缺少反馈。
- 前几关要有明显“捡到目标物”的正反馈。

#### 推荐规则

- 顶层和次顶层至少分布 `20% ~ 35%` 的绿豆。
- 每层随机但需做一次可玩性校验。
- 若首屏可见绿豆数为 0，则重新分布。

### 6.5 点击拾取方案

建议只给 **当前可见颗粒** 开启碰撞检测。

实现方式：

1. 为可见颗粒节点挂轻量碰撞体。
2. 使用 `PhysicsSystem.raycastClosest` 做点击检测。
3. 点击命中后播放拾取动画。
4. 逻辑层删除该颗粒。
5. 刷新与其关联的下层颗粒可见状态。

为什么不让所有颗粒都可点击：

- 隐藏颗粒本来不应被点击。
- 避免同时挂数千碰撞体造成开销。
- 简化射线命中逻辑。

### 6.6 拾取后的露出刷新

拾取后不要重新生成整堆，只刷新受影响颗粒。

建议流程：

1. 找到被拾取颗粒 `grainId`。
2. 遍历其 `supportsBelow`。
3. 对每个下层颗粒检查 `blockersAbove` 是否已全部移除。
4. 若全部移除，则设为 `exposed = true`。
5. 从对象池中激活该颗粒显示。

这样做的好处：

- 复杂度可控
- 露出顺序稳定
- 更接近“表层剥离”的体验

### 6.7 动画与特效

首版不追求复杂特效，重点做“轻、脆、爽”的点击反馈。

建议最低配置：

- 米粒点击：轻微抬升 + 缩放 + 飞出碗外消失
- 绿豆点击：飞入展示区槽位
- 露出新颗粒：淡入 + 微抬升
- 输入正确：碗、UI、关卡标签同步庆祝
- 输入错误：输入框抖动 + 红色提示
- 倒计时紧张阶段：UI 颜色切换 + 音效加重

### 6.8 性能策略

目标平台建议按中低端移动机型设计。

#### 客户端预算建议

- 同屏激活颗粒节点：`80 ~ 250`
- 总逻辑颗粒数：首版关卡模式建议 `50 ~ 300`
- 单局峰值 drawcall：尽量控制在 `80` 以内
- 主摄像机常驻，不频繁切换

#### 必做优化

- 对颗粒节点使用对象池
- 米粒与绿豆尽量共用材质
- 使用低面数模型
- 静态环境使用烘焙光照或近似静态灯光
- 避免使用高成本透明材质
- 尽量减少运行时动态创建材质

#### 不建议的做法

- 大量刚体
- 全量粒子碰撞
- 运行时频繁换 mesh
- 用骨骼动画表现米粒

## 9. 配置系统规划

### 9.1 关卡配置

建议使用 JSON 或 Scriptable 配置，首版先本地静态表，后续再支持远程。

示例：

```json
{
  "id": 10001,
  "riceRange": [50, 60],
  "beanRange": [5, 10],
  "timeLimit": 60,
  "displayZones": [2, 2, 5],
  "hintDelta": 1,
  "rewardExtraTime": 15,
  "topBeanRatioMin": 0.2
}
```

字段说明：

- `riceRange`：米粒生成区间
- `beanRange`：绿豆生成区间
- `timeLimit`：秒，`-1` 表示不限时
- `displayZones`：默认区域、分界区域、广告区域
- `hintDelta`：广告提示精度级别
- `rewardExtraTime`：广告加时秒数
- `topBeanRatioMin`：顶层豆子最低可见比例

### 9.2 成就配置

成就条件建议按统计字段驱动，不写死在代码中。

可支持条件：

- 累计开局次数
- 累计通关次数
- 关卡模式最大通关关卡
- 累计拾取米粒数量
- 累计拾取绿豆数量

### 9.3 广告配置

建议广告配置独立化：

- 错误答案提示广告
- 关卡超时加时广告
- 绿豆展示区解锁广告
- 结算页奖励广告

## 10. 本地数据与存档规划

### 10.1 本地存档内容

建议本地至少保存：

```ts
interface PlayerSaveData {
  version: number;
  playerId: string;
  guideFinished: boolean;
  unlockedLevelId: number;
  maxPassedLevelId: number;
  totalStartCount: number;
  totalWinCount: number;
  totalRiceCollected: string;
  totalBeanCollected: string;
  achievementStates: Record<string, boolean>;
  adUnlockStates: Record<string, number>;
  settings: {
    music: boolean;
    sound: boolean;
    vibration: boolean;
  };
}
```

说明：

- 大数值字段建议存字符串，避免后期精度问题。
- `adUnlockStates` 可记录当局或永久解锁状态，具体看设计。

### 10.2 单局数据

单局中建议维护 `LevelRuntimeData`：

- 当前关卡 id
- 实际生成米粒数
- 实际生成绿豆数
- 剩余时间
- 已拾取米粒数
- 已拾取绿豆数
- 已露出颗粒数
- 是否已使用广告提示
- 是否已使用广告加时

## 11. 成就系统规划

根据 PDF，成就系统是“无奖励纯收集”，因此应以低耦合方式实现。

建议流程：

1. 单局结算时汇总增量数据。
2. 写入本地统计。
3. 触发 `AchievementSystem.refresh()`。
4. 对比成就配置是否达成。
5. 若首次达成，弹出轻量提示。

注意：

- 成就判断不要放在点击过程中逐颗计算。
- 建议在关键节点批量刷新，降低性能消耗。

## 12. 地域排行与服务端规划

### 12.1 功能目标

根据 PDF，地域排行包含两层：

- 全国省份排行：按省份累计绿豆总数排序，展示前五。
- 省份内个人排行：每省前十。

### 12.2 权限与时机

建议在“完成新手引导后”请求定位权限。

流程：

1. 玩家完成新手关。
2. 弹权限引导。
3. 获取省份信息。
4. 绑定到玩家档案。
5. 后续仅上报增量统计，不必每次重复请求位置。

### 12.3 客户端上报策略

不要上报全量累计值，改为上报增量：

- 本局新增绿豆数
- 当前玩家所在省份
- 当前总关卡进度
- 时间戳

这样可以避免：

- 客户端被篡改后全量覆盖
- 大数字反复传输
- 服务端聚合成本不稳定

### 12.4 服务端数据结构建议

建议最少有以下表：

- `player_profile`
- `player_stats`
- `player_stat_log`
- `province_stat_total`
- `province_rank_snapshot`
- `province_player_rank_snapshot`

字段建议：

`player_profile`

- `player_id`
- `platform`
- `province_code`
- `create_time`

`player_stats`

- `player_id`
- `total_bean_collected`
- `total_rice_collected`
- `total_start_count`
- `total_win_count`
- `max_level_id`
- `update_time`

`province_stat_total`

- `province_code`
- `total_bean_collected`
- `update_time`

### 12.5 大数值处理建议

PDF 中明确提出数值可能极大。

建议：

- 客户端：使用字符串表示超大数。
- 服务端：使用 `BigInt` 或高精度数值类型。
- 排行内部存整数，不要存浮点。
- 展示层再格式化成科学计数法或中文数量级。

示例展示：

- `1.88915 x 10^27`
- 或者 `1.88e27`

### 12.6 服务端技术建议

如果是轻量首版，可选：

- `Node.js + TypeScript + PostgreSQL`
- `Node.js + Redis + MySQL`

如果目标平台是微信小游戏，建议服务层额外封装：

- 玩家登录态校验
- 广告回调校验
- 省份归属映射
- 排行快照接口

## 13. 广告与社交规划

### 13.1 激励广告触点

根据 PDF，首版至少支持三个广告触点：

1. 错误答案后获取数量提示。
2. 超时后获取额外时间。
3. 解锁更多绿豆展示区。

建议再预留一个：

4. 结算翻倍或额外奖励位。

### 13.2 广告接入方式

不要在业务逻辑中直接调用平台广告 API。

建议结构：

- `AdSystem` 负责广告业务状态
- `PlatformAdapter` 负责具体平台广告 SDK
- UI 层只发起“请求看广告”
- 结果通过事件回流玩法层

### 13.3 绿豆展示区规则

根据 PDF，绿豆即使超出当前可见解锁区，也算已经拾取成功，只是暂时不展示。

因此数据结构必须拆为两套：

- `collectedBeanCount`：真实已拾取数
- `displayUnlockedCount`：当前可展示容量

这样广告解锁后只需要“补显示”，不需要补逻辑领取。

### 13.4 社交分享

首版建议只做轻分享：

- 分享当前关卡成绩
- 分享省份排行位置
- 分享成就截图

不要把分享绑死在核心通关流程里。

## 14. 平台适配规划

由于 PDF 中出现微信语境，建议从一开始就做平台抽象。

接口建议：

interface IPlatformAdapter {

- `WechatPlatformAdapter`：小游戏正式接入

## 15. 美术与技术美术规划

### 15.1 美术风格建议

适合做“轻拟物 + 干净桌面”的风格，不建议走重写实。

原因：

- 米粒和绿豆数量多，重写实对移动端压力较大
- 轻拟物更适合休闲化和广告化表现
- 更容易做清晰的交互识别

### 15.2 资源建议

- 碗：1 个主模型，少量材质变化
- 米粒：1 个低模主模型 + 2 个轻微随机缩放变体
- 绿豆：1 个主模型 + 换色能力
- 桌面：1 个静态模型或平面贴图
- 特效：2D/3D 混合粒子即可

### 15.3 技术美术注意点

- 统一材质球数量
- 统一颗粒尺寸基准
- 控制法线与高光，避免米粒发灰
- 绿豆需要明显高于米粒的识别度

## 18. 风险与应对

### 18.1 3D 粒子性能风险

风险：

- 数量上来后节点、碰撞体、动画会拖慢帧率

应对：

- 对象池
- 仅激活可见层
- 逻辑层与显示层分离
- 优先验证极限数量压测

### 18.2 点击精度风险

风险：

- 粒子小、密度高，误触概率高

应对：

- 放大点击碰撞体
- 点击高亮
- 固定镜头
- 必要时增加吸附判定

### 18.3 排行大数值风险

风险：

- 省份累计值极大，客户端精度溢出

应对：

- 客户端存字符串
- 服务端高精度聚合
- 显示层格式化

### 18.4 平台权限风险

风险：

- 用户拒绝位置权限，导致地域排行缺少归属

应对：

- 提供“未授权省份池”
- 后续允许二次授权
- 排行页兼容匿名或未定位状态

### 18.5 广告依赖风险

风险：

- 广告加载失败影响流程体验

应对：

- 广告失败时给一次兜底奖励
- 广告位做冷却和重试
- 核心流程不可被广告完全阻塞

## 19. 验收标准

首版至少满足以下验收标准：

1. 可以稳定进入关卡并生成 3D 粮食堆。
2. 玩家能够点击上层颗粒并触发正确拾取反馈。
3. 拾取上层后，下层颗粒能正确露出。
4. 绿豆全部拾取后可输入答案。
5. 答案正确可通关并解锁下一关。
6. 错误答案可触发广告提示。
7. 超时可触发广告加时。
8. 本地存档可恢复关卡进度和累计统计。
9. 成就可根据累计数据正确解锁。
10. 地域排行可展示省榜和省内个人榜。
11. 中低端机型长时间游玩不出现明显卡顿或崩溃。

## 20. 推荐实施顺序

建议按以下顺序开发，而不是并行乱铺功能：

1. 先做 3D 堆叠原型，验证“可玩”。
2. 再做关卡流程，验证“能通关”。
3. 再做存档和成就，验证“能累计”。
4. 再做广告和排行，验证“能运营”。
5. 最后做调优和包装，验证“能上线”。

## 21. 针对当前工程的直接落地建议

结合当前仓库，下一步建议立刻执行以下工作：

1. 新建 `assets/scripts/game` 目录，建立业务层骨架。
2. 在主场景中正式拆出 `WorldRoot`、`Canvas/UIRoot`。
3. 编写 `LevelGenerator` 原型，只做 50 粒米 + 5 粒豆测试。
4. 编写 `GrainPicker`，完成点击拾取。
5. 编写 `LevelHUD`，显示倒计时和拾取数。
6. 做一个最小可玩的新手关。
7. 跑通首个通关闭环后再接广告和排行。

## 22. 最终建议

这个项目最关键的不是“3D 做得多真”，而是三件事：

- 颗粒堆叠是否稳定、可点击、可露出
- 关卡节奏是否足够短平快
- 广告、排行、成就是否与主循环自然融合

因此，开发策略应当是：

- 用 3D 提升表现，而不是把成本压到真实物理上
- 用逻辑堆叠保证性能和可控性
- 用清晰的模块边界，避免后续广告、平台、排行把玩法代码污染掉

如果按本文档推进，这个项目适合先做成一个 **轻量、可持续迭代的 3D 休闲点击数数游戏**，而不是一开始就把全部玩法和运营功能一次性做满。
